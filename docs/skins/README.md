# 스킨 헌법 (Skin constitutions)

SECS 2R의 세 스킨이 각자 무엇을 믿고, 무엇을 금지하며, 새 구성 요소가 생길 때 어떻게 답해야 하는지를 적은 문서 묶음입니다. 절차(`data-skin` 축, 파일 구조, 증거)는 [ADR 0010](../adr/0010-skin-sets.md)에 있고, 토큰의 정본은 [`DESIGN.md`](../DESIGN.md)입니다. 이 디렉터리는 **디자인 철학 그 자체**를 보존합니다.

Hardware Rack과 Signal Matrix의 헌법은 같은 유지보수자의 [EqualizerAPO-XT](https://github.com/115dkk/EqualizerAPO-XT) `docs/skins/`(Qt Editor의 스킨 프로그램과 픽커 라운드가 쌓은 판례)에서 옮겨 왔고, Qt 위젯의 조문을 React·CSS의 재료로 다시 썼습니다. 원문의 판례 태그(AR1, M3 등)는 그 판정의 이유가 SECS 2R에도 그대로 서는 자리에만 남겼습니다.

| id | 이름 | 한 줄 정체성 | 헌법 문서 |
|---|---|---|---|
| (없음) | Instrument | 차분하고 정밀한 계측기. 데이터가 있는 곳만 촘촘하고 나머지는 조용하다 | [default.md](default.md) |
| `rack` | Hardware Rack | 19인치 랙의 앰프 페이스플레이트. 손에 닿을 듯한 기계 | [rack.md](rack.md) |
| `matrix` | Signal Matrix | 공항 출발 안내판 / 방송 라우팅 매트릭스. 좌표를 가진 셀의 보드 | [matrix.md](matrix.md) |

## 세 스킨이 함께 지키는 것

각 헌법은 아래 공통 기반 위에서만 갈라집니다.

- **차별화 게이트.** 어떤 항목에서든 두 스킨이 "팔레트만 다르면" 실패입니다. 새 구성 요소(카드, 단추, 알약, 값 칸, 그래프 등)가 생기면 세 스킨이 각자의 철학으로 **따로** 답하고, ADR 0010의 여덟 항목(단계 레일, 주 동작, 카드 chrome, 상태 표기, hover와 focus, 비활성, 숫자 판독, 그래프 바탕)으로 심사합니다.
- **토큰만 사용.** 색은 `tokens.css`의 역할 이름으로만 씁니다. 스킨 파일은 그 이름을 덮어쓰고, 스킨만의 값은 `--skin-` 접두어로 둡니다. 구성 요소 CSS에 색 값을 쓰지 않는 규칙은 스킨 파일에서도 같습니다(색 값은 토큰 블록에만 있고, 구조 재정의는 토큰을 읽습니다).
- **중립 기본값 규칙.** 기본 스킨은 `data-skin`이 없는 상태입니다. 스킨을 위해 구성 요소에 무언가를 더할 때(상태 속성, 의사 요소가 붙을 자리) 기본 스킨의 그림은 픽셀 단위로 같아야 하고, 갤러리 스크린샷의 비교로 증명합니다(가정하지 않습니다).
- **상호작용 계층은 공유합니다.** DOM, 핸들러, `aria-*`, 초점 순서, 단축키, `data-ui` id, 문구는 구성 요소의 것이고 스킨은 표현만 바꿉니다. 스킨은 요소를 숨기거나 순서를 바꾸지 않습니다(`display: none`, `order` 금지). 예외는 kit이 한 뜻을 글과 기호의 두 표현으로 모두 그려 둔 자리에서 스킨이 하나를 고르는 것입니다(배치도의 스크린 캡션과 `map__front` 기호). 그것은 숨김이 아니라 선택이고, 그런 자리는 kit의 CSS 주석과 `docs/DESIGN.md`가 밝힙니다.
- **하한은 공유합니다.** 글자 14px(캡션 13px), 누르는 영역 40px, 키보드 초점의 가시성, 줄인 움직임에서 시간 0. 스킨은 내리지 못합니다.
- **갤러리가 증거입니다.** `gallery-shots.mjs`가 스킨×밝게·어둡게의 견본을, `screen-tour.mjs`가 스킨의 어두운 한국어 화면을 찍습니다. 외형 변경은 그림으로 확인하고, 무간섭 주장은 그림 비교로 증명합니다.
- **대비는 측정합니다.** `contrast.test.ts`가 스킨마다 글자 4.5:1, 테두리·초점·글리프 3:1을 계산합니다. 미달이면 색상을 바꾸지 말고 명도를 움직입니다.

## 공유 조문

아래 조문은 특정 스킨의 표현이 아니라 세 스킨이 함께 지키는 규범입니다. 각 헌법 문서는 이 조문을 되풀이하지 않고 자기 스킨의 형태만 답합니다.

1. **상태는 한 번 말합니다.** 판정을 그 스킨의 상태 표기(알약의 점, 베젤 LED, 보드의 램프)가 들고 있으면 그 옆에 같은 뜻의 장식을 더 붙이지 않습니다. 문구는 명사구 하나입니다.
2. **문제는 스킨의 상태 문법이 먼저 말합니다.** 긴 설명문 단독으로 문제를 알리지 않습니다. 각 스킨의 상태 표기가 먼저 말하고, 문장은 원인과 다음 행동만 짧게 잇습니다(`ErrorNotice`의 구조는 공유).
3. **폭 압박의 우선순위.** 1024×700 최소 틀에서 넘치면 데이터(이름, 경로)가 말줄임으로 먼저 물러나고, 동작의 라벨은 마지막까지 온전합니다. 잘린 동작은 아무것도 전하지 못하지만, 줄어든 데이터는 툴팁이 받칩니다.
4. **방향·캐럿 글리프는 아이콘으로 그립니다.** 글꼴 커버리지가 화살표의 존재를 정하게 두지 않습니다. 텍스트로 쓰는 화살은 ASCII만 허용합니다.
5. **컨트롤은 그 스킨이 가르친 '누를 수 있는 형태'를 입습니다.** 맨 외곽선이나 투명 캡션 단독은 단추로 읽히지 않습니다. 그 스킨의 캡·셀·필이 이미 가르친 휴지 형태를 재사용해야 학습 비용 없이 컨트롤로 읽힙니다.
6. **강조는 하나입니다.** 포인터가 항목 위로 가면 그 항목이 키보드로 고른 것과 같은 현재 항목이 됩니다(메뉴, 목록, 배치도). 호버만의 옅은 표현을 따로 두지 않습니다.
7. **색은 상태에만 삽니다.** success·warning·danger·info는 정해진 뜻(DESIGN.md §2.3)으로만 쓰고, 장식과 타입 식별에 쓰지 않습니다. 강조색은 '누를 수 있음'과 '지금 고른 것'입니다.
8. **문구는 공유합니다.** 각인풍 대문자는 `text-transform`으로만 하고 카탈로그 문장은 바꾸지 않습니다. 한국어에는 대소문자가 없으므로 자간과 굵기로 같은 인상을 냅니다.

## 헌법 문서의 사용법

새 구성 요소나 화면을 추가할 때는 세 헌법의 **"새 요소를 이 스킨답게 만드는 법"** 체크리스트에 답하는 방식으로 설계합니다. 문서가 코드와 어긋나면 코드가 아니라 문서를 의심하되, "하지 말 것" 절은 코드보다 오래 삽니다. 그 절은 실수 사례나 기각된 설계에서 나온 것이므로 코드에 위반 사례가 없다는 이유로 지우지 않습니다.
