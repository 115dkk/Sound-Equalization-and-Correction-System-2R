# ADR 0010: 스킨 셋 (기본 · Hardware Rack · Signal Matrix)

- 상태: 채택 (2026-10-22)
- 관련: [ADR 0003](0003-stack-and-ipc.md)의 화면 규칙, [`docs/DESIGN.md`](../DESIGN.md), [`docs/skins/`](../skins/README.md)

## 맥락

SECS 2R의 화면은 토큰 한 벌(밝게·어둡게, 튜토리얼 강조색)로 그립니다. 두 가지 요청이 함께 들어왔습니다.

1. 기본 스킨의 강조색(청록, 색상 195)이 업스트림 화면과 앱 아이콘에서 왔다는 근거는 있지만, 사용자는 그 색을 유행색처럼 느낍니다. make-interfaces-feel-better의 `color.md` 점검표로 기본 스킨을 감사해 달라는 요청입니다.
2. EqualizerAPO-XT의 Editor에는 다섯 스킨이 각자 무엇을 믿고 무엇을 금지하는지 적은 헌법과 판례(`docs/skins/`)가 쌓여 있습니다. 그중 **Hardware Rack**과 **Signal Matrix** 두 컨셉을 SECS 2R로 옮겨, 스킨 셋이 팔레트만 다른 것이 아니라 서로 다른 UI를 가지게 해 달라는 요청입니다.

EqualizerAPO-XT의 스킨은 Qt 위젯과 QPainter로 그리고, `ISkin` 훅과 행 재생성으로 전환합니다. SECS 2R의 화면은 React와 CSS 커스텀 프로퍼티이고, 구성 요소의 CSS에는 색 값이 없으며(`tokens.test.ts`), 상호작용(핸들러, aria, 초점)은 구성 요소가 쥡니다. 같은 철학을 다른 재료로 구현해야 합니다.

## 결정

### 1. 스킨은 `data-skin` 속성 하나다

스킨은 테마(`data-theme`)와 강조색(`data-accent`)과 독립인 세 번째 축입니다. 값은 `rack`과 `matrix`이고, 기본 스킨은 속성이 없는 상태입니다(중립 기본값: 스킨 코드가 한 줄도 없을 때의 화면이 곧 기본 스킨). 앱은 `<html>`에, 갤러리는 견본마다 겁니다(`PrefsScope`). 고른 스킨은 `AppSettings.skin`(`AppSkin`: `default` · `rack` · `matrix`)에 저장되어 다시 켜도 남습니다. `skin` 필드가 없는 이전 설정 파일은 `default`로 읽습니다.

### 2. 스킨은 CSS 한 파일이고 토큰부터 다시 정한다

스킨 하나는 `apps/secs2r/ui/src/styles/skins/<id>.css` 한 파일입니다. 파일은 두 부분으로 이루어집니다.

- **토큰 재정의.** `[data-skin="<id>"]`(밝게), `[data-skin="<id>"][data-theme="dark"]`와 `@media (prefers-color-scheme: dark) { [data-skin="<id>"]:not([data-theme="light"]) }`(어둡게 두 벌, 서로 같아야 함)에서 `tokens.css`의 이름 가운데 필요한 것을 덮어씁니다. 강조색은 `--accent-hue`·`--accent-chroma`·`--accent-l` 같은 입력값을 덮어 조립 규칙(`:root, [data-theme], [data-accent], [data-skin]`)이 다시 조립하게 하고, 튜토리얼 강조색보다 우선하려면 `[data-skin="<id>"][data-accent]`에도 같은 값을 둡니다. 스킨만 쓰는 토큰은 `--skin-` 접두어를 씁니다(예: `--skin-bevel-light`, `--skin-grid-pitch`). 색 값은 `tokens.css`와 `styles/skins/*.css`에만 있습니다.
- **구조 재정의.** `[data-skin="<id>"] .ui-button` 같은 선택자로 구성 요소와 틀의 모양(모서리, 경계, 깊이, 질감, 글자 처리, 상태 표현)을 바꿉니다. 그림은 그라디언트와 의사 요소(`::before`, `::after`)로 그리고 이미지 에셋을 들이지 않습니다.

스킨은 DOM을 바꾸지 않습니다. 구성 요소의 마크업, 핸들러, `aria-*`, 초점 순서, `data-ui` id, 문구는 세 스킨이 공유하며, 표현만 스킨의 몫입니다. 스킨이 표현하려는 상태가 DOM에 없으면 스킨을 바꾸지 말고 구성 요소에 상태 속성을 더합니다(그때는 기본 스킨이 바뀌지 않음을 갤러리 스크린샷으로 보입니다).

### 3. 차별화 게이트

두 스킨이 어느 항목에서든 "팔레트만 다르면" 실패입니다. 새 구성 요소나 화면이 생기면 세 스킨이 각자의 철학으로 **따로** 답하고, 아래 여덟 항목으로 심사합니다. 판정은 `docs/skins/README.md`의 심사 기록에 쌓입니다.

| # | 항목 | 심사 질문 |
|---|---|---|
| 1 | 단계 레일 | 단계와 그 상태(완료·지금·막힘·건너뜀)를 무엇으로 말하는가 |
| 2 | 주 동작 | 화면마다 하나인 채운 단추가 어떤 '누를 수 있는 형태'인가 |
| 3 | 카드 chrome | 모서리·경계·깊이의 언어가 무엇인가 |
| 4 | 상태 표기 | 알약·점·띠가 상태를 어떻게 말하는가 |
| 5 | hover와 focus | 포인터와 키보드가 닿았을 때 무엇이 변하는가 |
| 6 | 비활성 | 못 누르는 것이 어떻게 보이는가 |
| 7 | 숫자 판독 | 값 칸·표의 숫자·미터의 재질과 활자가 무엇인가 |
| 8 | 그래프 바탕 | 그래프의 바탕·모눈·축 글자가 어떤 계기인가 |

### 4. 세 스킨이 함께 지키는 것

- 글자 14px 하한(캡션 13px), 누르는 영역 40px, 키보드 초점의 가시성, `prefers-reduced-motion`의 시간 0. 스킨은 이 하한을 내리지 못합니다.
- 상태색(success·warning·danger·info)은 상태에만 씁니다. 강조색은 상태색과 15° 이상 떨어지고, 중립색은 한 기운을 유지합니다(`contrast.test.ts`의 색 규율 검사).
- 모든 글자 쌍 4.5:1, 입력칸 테두리·초점 고리·상태 글리프 3:1 이상을 측정으로 지킵니다. 수치는 추정하지 않고 `contrast.test.ts`가 OKLCH→sRGB 변환과 감마 매핑으로 계산합니다.
- 문구는 공유합니다. 스킨이 각인풍 대문자를 쓰더라도 CSS `text-transform`으로만 하고 카탈로그 문장은 바꾸지 않습니다. 한국어에는 대소문자가 없으므로 그 스킨은 자간과 굵기로 같은 인상을 냅니다.

### 5. 증거

- 갤러리 견본은 기본(밝게·어둡게, 한국어·영어, 튜토리얼)에 더해 Rack과 Matrix를 밝게·어둡게 한국어로 찍습니다(`gallery-shots.mjs`, 9개 변형). 화면 투어는 Rack과 Matrix의 어두운 한국어 화면을 더 찍습니다(`screen-tour.mjs`, 6개 변형). `ui-gallery.yml`의 리뷰 이슈가 그 그림을 보여 줍니다.
- 스킨 파일의 어두운 두 벌이 같은지, 밝게·어둡게가 같은 색 토큰을 덮는지, 대비와 색 규율은 `contrast.test.ts`가 검사합니다.
- 스킨 선택이 저장되고 다시 켜도 남는지는 서비스 테스트(`app_settings_are_versioned_bounded_and_capped`)와 화면 테스트가 확인합니다.
- 이 작업은 Superloopy의 솔로 증거 루프(`.superloopy/`, 커밋하지 않음)로 기준마다 명령 증거를 남기며 진행했습니다. 뒤의 스킨 작업도 같은 방식으로 기준과 증거를 적습니다.

## 결과

- 새 구성 요소마다 세 가지 답이 필요합니다. 비용을 줄이려고 스킨 재정의는 토큰으로 할 수 있는 것을 토큰으로 먼저 하고, 구조 재정의는 차별화 게이트의 여덟 항목에 집중합니다.
- 갤러리 스크린샷이 5개 변형에서 9개로, 투어가 4개에서 6개로 늘어 CI의 `gallery` 잡과 `ui-gallery.yml`이 그만큼 더 걸립니다.
- 설정 팝오버에 '스킨' 항목이 생깁니다(언어, 테마, 스킨, 로고 순).
- 기본 스킨의 강조색이 바뀌므로 로고의 짙은 청록 타일과 강조색이 더는 같은 색상이 아닙니다. 로고는 그림이고 강조색은 '누를 수 있음'의 색이라 뜻이 다르며, 이 결정은 `docs/skins/default.md`의 감사 기록에 적습니다.

## 검토한 대안

- **팔레트 변형만 두기.** 토큰 값만 다른 테마를 여럿 두는 쪽이 싸지만, 헌법의 차별화 게이트를 처음부터 포기하는 것이라 기각했습니다.
- **Qt처럼 페인터 훅 두기.** 구성 요소가 스킨 객체를 받아 그리는 방식은 React에서 모든 구성 요소에 분기를 심습니다. CSS 캐스케이드가 이미 표현을 바깥에서 덮는 장치이므로 쓰지 않았습니다.
- **스킨마다 별도 구성 요소 트리.** 상호작용 계층이 셋으로 갈라져 접근성과 테스트가 셋이 됩니다. 기각했습니다.
