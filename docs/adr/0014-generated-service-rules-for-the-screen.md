# 0014. 화면과 모의 서비스는 서비스 규칙을 생성 파일로 받는다

상태: 채택, 2026-10-25

## 배경

ADR 0003은 IPC 요청과 응답의 타입을 `secs-types`에서 ts-rs로 생성하게 했습니다. 타입은 한 곳에서 오지만 값은 그렇지 않습니다. 설정 칸의 한도는 서비스의 `settings_edit.rs`, 화면의 `screens/calibrate/settingsView.ts`의 `LIMITS`, 모의 서비스 `ipc/mock.ts`의 `editSettings`에 세 벌로 있고, 스윕 길이, 최근 프로젝트 개수, XO 묶음 이름, 내보내기 폴더 이름 규칙도 화면이나 모의 서비스에 손으로 옮겨져 있습니다. 감사 #92(C13)에서 이 사본 가운데 셋이 서비스와 이미 달랐습니다. 화면 테스트와 견본은 모의 서비스를 거치므로 테스트가 그 어긋난 값을 정답으로 고정했고, 작업서마다 모의 서비스를 손으로 다시 맞추는 일이 반복됐습니다.

## 결정

- **규칙 상수는 `secs-types`의 `rules` 모듈이 정본입니다.** 설정 칸 한도, 스윕 길이, 최근 프로젝트 최대 개수처럼 서비스가 판정에 쓰고 화면이 보여 주는 값을 이름 있는 상수로 둡니다. 서비스는 숫자를 다시 적지 않고 이 상수를 씁니다. 결과는 비트 단위로 그대로입니다.
- **값도 생성합니다.** `cargo test -p secs-types`가 타입 바인딩과 함께 `apps/secs2r/ui/src/ipc/bindings/rules.ts`에 상수 값을 씁니다. CI의 바인딩 비교(ADR 0003)가 이 파일도 함께 비교하므로 새 CI 단계는 없습니다. 화면과 모의 서비스는 이 파일을 가져다 쓰고 같은 값을 다시 적지 않습니다.
- **입력이 없는 규칙 응답은 서비스에서 기록합니다.** 프로젝트 상태에 기대지 않고 서비스가 계산해 돌려주는 응답(모드 사양, 구성 프리셋, 타깃 프리셋, 고정 시각의 내보내기 폴더 이름 같은 것)은 `secs-service`의 테스트가 `Service::call`로 받아 `apps/secs2r/ui/src/ipc/recorded/`에 JSON으로 둡니다. 테스트는 저장소 사본과 비교해 다르면 실패하고, `SECS_RECORD=1`로 돌리면 다시 씁니다. 모의 서비스는 이 기록을 그대로 돌려줍니다.
- **모의 서비스는 계약만 맡습니다.** 봉투, 잡 스케줄러와 진행 이벤트, 실패 주입, 되돌리기, 열린 프로젝트의 상태 보관이 모의 서비스의 몫입니다. 서비스 규칙을 다시 구현한 함수는 생성 상수나 기록 응답으로 바꾸고, 그 사본이 서비스와 같은지 보던 테스트는 지웁니다.
- **견본 투어는 기록 위에서 상태를 바꿉니다.** `gallery/tour/scenes.ts`는 편집을 이어 가야 하므로 기록 응답을 출발점으로 삼고, 장면이 바꾼 상태는 지금처럼 모의 서비스가 보관합니다.

## 결과

- 서비스 규칙이 바뀌면 `cargo test -p secs-types`나 서비스 기록 테스트가 바로 실패하므로, 화면과 모의 서비스가 낡은 값을 쥔 채로 지나가지 않습니다.
- 모의 서비스 코드와 픽스처가 줄고, 모의 서비스를 다시 맞추는 작업서가 필요 없어집니다.
- 기록 파일은 서비스 출력이므로 사람이 고치지 않습니다. 기록을 바꾸는 변경은 서비스 변경과 같은 커밋에 담깁니다.
- 기록은 입력이 없는 응답에만 씁니다. 측정이나 계산 결과처럼 프로젝트에 기대는 응답은 지금처럼 모의 서비스의 픽스처가 만들고, 그 값은 화면을 그리기 위한 견본일 뿐 서비스 규칙의 사본이 아닙니다.
