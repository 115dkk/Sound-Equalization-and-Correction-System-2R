# 0009. 화면 결과와 필터 원본을 분리하고 완료 작업 기록을 제한한다

상태: 채택, 2026-10-20

## 배경

화면은 보정 결과의 채널 역할과 MIMO 경로·입력·탭 수를 사용하지만,
`CalibrationSummary.chain`과 `MimoSummary.paths`는 실제 FIR 배열까지 담았습니다.
132개 경로에 8,000탭씩 있으면 1,056,000개의 f64 값이 요약에 섞입니다.
완료 이벤트와 이후 `results` 조회가 이 결과를 중복 전달했고, Rust 잡 기록과
화면 세션의 잡 목록은 완료 결과를 계속 보관했습니다.

파일 내보내기는 Rust가 수행합니다. 화면용 요약에 DSP 원본을 넣을 이유가
없으며, 네이티브 화면으로 옮기더라도 잡 기록의 수명은 별도로 제한해야 합니다.

## 결정

- `CalibrationSummary`는 필터 사슬 대신 `main_roles`와 `sub_roles`를 보냅니다.
  기존 성적표, 지연, 실행 설정, 낡음과 안내 정보는 유지합니다.
- `MimoSummary`는 필터 경로 대신 `input_count`를 보냅니다.
  `support_count`와 `fir_taps_total`을 화면의 정본 개수로 사용합니다.
- DSP 원본은 Rust의 최신 계산 결과와 내부 영속 캐시에만 둡니다. 캐시의
  내보내기용 사슬은 화면 요약에서 분리하고, 이전 캐시는 읽을 때 이주합니다.
- 보정·MIMO 완료 이벤트의 `JobResult`는 종류만 있는 완료 표식입니다.
  화면은 완료 뒤 `results`를 한 번 조회합니다. XO 추천, 레벨 확인, 내보내기처럼
  별도의 결과 조회가 없는 작업은 작은 일회성 완료 값을 계속 보냅니다.
- `JobSnapshot`은 상태·진행·오류만 가집니다. 성공 결과를 작업 기록에 저장하지
  않습니다. 완료 이벤트의 값은 필요한 화면 상태로 옮기고 잡 목록에는 넣지 않습니다.
- Rust 레지스트리와 화면 잡 목록은 최근 완료 작업 32개 및 모든 진행 중 작업을
  보존합니다. 완료 순서로 오래된 기록을 제거하며 실행·취소 중 작업은 제거하지
  않습니다. 기존 로그 기록의 200개 상한도 유지합니다.
- 작업 메타데이터 이력은 앱 전체에서 위 상한으로 유지합니다. 프로젝트 교체가
  진행 중 작업의 추적이나 완료 이벤트를 끊지 않으며, 완료한 요청 문맥은 즉시
  정리합니다. 이전 프로젝트 작업의 늦은 결과가 새 프로젝트를 덮어쓰지 않도록
  세션 식별자를 확인합니다. 시작 응답보다 빠른 완료는 보존하고, 중복 완료
  이벤트는 결과 재조회를 중복 실행하지 않습니다.
- 서비스는 각 잡의 시작을 한 번 알리고, Tauri 채널은 그 잡 안의 이벤트 순서를
  유지합니다. 서로 다른 잡의 ID 배정과 알림 도착 순서는 다를 수 있습니다.
  처음 받은 시작 알림이나 요청의 성공 응답은 ID가 작다는 이유로 버리지 않습니다.
  오래된 스냅샷의 재등장 방어와 새 활성 작업의 수락은 구분합니다.
- 내부 캐시는 64 MiB로 제한합니다. 132×8,000개의 계수는 단일 JSON 원본으로도
  기존 8 MiB를 넘을 수 있으므로 중복 제거만으로는 충분하지 않습니다.
  저장은 크기가 제한된 임시 파일에 직접 직렬화한 뒤 교체하고, 화면 요약에는
  이 원본을 넣지 않습니다. 직렬화와 파일 쓰기 동안 세션·결과 잠금을 유지하지 않습니다.

## 검증

대형 합성 FIR의 실제 JSON 바이트와 완료 이벤트 크기를 전후 비교합니다.
반복 완료·실행 중 작업·프로젝트 교체·빠른 완료의 회귀 테스트를 둡니다.
이전 캐시 재열기와 파일 내보내기로 필터 원본이 유지되는지도 확인합니다.
JSON 크기, JavaScript 힙, 실제 WebView 정지 시간은 서로 다른 측정값으로
다루며, 측정하지 않은 실행 시간이나 메모리 사용량을 추정치로 대체하지 않습니다.
