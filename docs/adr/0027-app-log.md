# 0027. 앱 로그

상태: 채택, 2026-10-31

## 배경

0.41.0을 쓰는 사용자가 오픈채팅으로 결함을 알려 왔습니다(2026-10-31). 무엇을 눌렀고 어떤 계산이 어떻게 끝났는지는 스크린숏과 말로만 전해졌고, 재현은 사례 데이터로 따로 해야 했습니다. 데스크톱 앱에는 로그 파일이 없습니다. 백그라운드 호스트(`secs2r-host`)만 `host.log`를 저장하고, 앱은 시작에 실패할 때 `eprintln!` 한 줄을 출력할 뿐인데, 출시판은 콘솔이 없는 GUI 프로그램이라 그 줄도 보이지 않습니다. 유지보수자는 로그 기능을 만들어 두기로 했습니다.

## 결정

### 위치와 크기

- 앱 설정 폴더(`app_config_dir`) 아래 `logs/secs2r.log`에 저장합니다. 파일이 2 MiB를 넘으면 `secs2r.1.log`로 밀고, 오래된 파일은 `secs2r.4.log`까지 둡니다(최대 약 10 MiB).
- 새 의존성 없이 표준 라이브러리로 구현합니다. 항목마다 바로 파일에 기록하고(버퍼에 오래 두지 않음), 기록에 실패해도 앱은 멈추지 않습니다.

### 형식

- 한 줄에 한 항목, UTF-8입니다. `2026-10-31T21:05:12.345+09:00 INFO job 7 calibrate started`처럼 현지 시각(오프셋 포함), 수준(`INFO`, `WARN`, `ERROR`), 영역, 내용 순서입니다.
- 키와 값은 `key=value`로 붙이고, 값에 공백이 있으면 큰따옴표로 감쌉니다.

### 기록하는 것

- **앱 시작:** 앱 판, 운영체제와 아키텍처, 고른 계산 장치(GPU 이름 또는 CPU)입니다.
- **작업:** 서비스 관찰자(`Deps::observer`)로 들어오는 작업 이벤트 가운데 시작(종류), 엔진의 기록 코드와 매개변수(`JobEvent::Log`), 끝(상태, 걸린 시간, 오류 코드와 메시지)입니다. 진행률과 입력 레벨(`Progress`, `Meter`)은 너무 잦으므로 기록하지 않습니다.
- **요청 오류:** `secs_call`의 결과가 오류 봉투일 때 메서드 이름과 오류 코드, 메시지입니다. 요청의 매개변수는 기록하지 않습니다.
- **보정 설정:** 보정과 MIMO 작업이 시작할 때 설정의 엔진 키(`engine_key`)입니다. 같은 결과를 다시 만들 때 필요한 설정이 이 한 줄에 들어 있습니다.
- **패닉:** 패닉 훅에서 메시지, 위치, 백트레이스를 기록한 뒤 원래 훅을 호출합니다.

### 기록하지 않는 것

측정 데이터와 결과 곡선, 요청 매개변수, 프로젝트 내용은 기록하지 않습니다. 경로 문자열 안의 사용자 홈 폴더는 `~`로 바꿉니다. 로그는 사용자의 컴퓨터에만 있고, 앱은 로그를 외부로 전송하지 않습니다.

### 화면

앱 설정 화면에 '로그 폴더 열기'를 두고, 그 옆에 문제를 알릴 때 이 폴더의 `secs2r.log`를 함께 보내 달라는 한 문장을 둡니다. 로그 폴더 경로는 시작 정보(`BootstrapInfo`)로 화면에 전달하고, 폴더는 이미 있는 `open_folder`로 엽니다.

## 결과

- 사용자가 결함을 알릴 때 로그 파일 하나로 무엇이 어떻게 끝났는지 전할 수 있습니다.
- 작업 이벤트마다 한 줄이라 계산 시간에는 거의 영향이 없습니다.
- 엔진 계산은 바뀌지 않습니다. 로그 파일을 다루는 코드는 앱(`apps/secs2r`)에만 있고, 공개 크레이트에는 시작 정보의 로그 폴더 경로 필드 하나만 추가됩니다.
